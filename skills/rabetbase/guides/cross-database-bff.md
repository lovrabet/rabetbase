# 跨库 Backend Function 查询与拼接

用于编写或审查跨数据库连接的 BFF 查询：分别读取各数据源，在可信 BFF 中按完整关联键拼接，再输出业务结果。单表优先使用 InstantAPI；同一连接内的关联或聚合可使用已确认支持的关联查询或 Custom SQL。跨库 Relation 描述逻辑关联，不赋予自动 JOIN、访问授权或分布式事务能力。

本文同库／跨库按平台数据库连接区分；不同 dblink 不因库名或表名相同而视为同库。默认关联关系指同库关联关系。

## 先确认事实和业务合同

1. 用 `rabetbase dataset detail --code <datasetCode> --format compress` 核对两端字段、类型、物理表和连接；模型访问方式遵循 [Backend Function](backend-function.md)，同名表必须消歧。连接身份以当前应用的真实 dblink 为准，不靠库名或表名推断。
2. 用 [跨库关系命令](../references/rabetbase-dataset-cross-relations.md)的 `cross-relation-list` 查询平台已登记关系。业务文档中的关系说明不代表已经登记；平台配置也不能代替业务正确性确认。两者冲突时报告端点差异，由业务确认后再维护关系，不能自动照搬或修正。
3. 在业务项目明确：完整关联键及顺序、基数、允许缺失与否、目标字段用途（展示、筛选、排序、统计）、各端访问范围、返回字段，以及读取预算和失败处理。具体映射留在业务项目，详细元数据按需查询；不在通用 Skill 中保存项目关系清单或元数据快照。

依据按需查找：先读已有接口文档和当前元数据，确认调用能力与硬限制；再读项目业务合同和现有配置，确定关联语义、授权及读取预算。已有事实充分时直接采用，不重复要求用户确认。依据冲突或缺少影响正确性、授权、完整性的必要信息时，说明具体缺口后确认；不自行发明权限字段、运行时上限或项目级配置。

当前 `cross-relation-create/update/delete` 每端只接收一个字段。复合键必须作为有序字段组整体理解，不能拆成多条单字段 Relation，也不能用逗号拼接字段来冒充复合关系支持。BFF 可依据已确认的业务合同实现完整键匹配，但不得宣称该复合关系已由这些命令登记。

## 根据查询语义选择执行顺序

| 外表的用途 | 执行方式 | 结果要求 |
|---|---|---|
| 仅补充展示字段 | 先对已授权主表筛选、稳定排序、计数和分页，再批量读取当前页所需外表数据 | 保留主记录、主表顺序和总数；一对多用约定的集合承载，不能展开后仍沿用原分页含义 |
| 参与筛选 | 先分析完整筛选表达式；能够等价转成目标键条件时，在预算内完整取得所需键集合，再保留原布尔逻辑筛选、计数和分页主表 | 主表 total 对应最终筛选结果；不能等价表达时报告能力边界 |
| 参与排序或统计 | 先确认能够覆盖完整相关结果集的执行方案 | 当前页拼接后的排序或统计不能冒充全局结果；预算不足时请求调整范围或由权威查询服务承接 |

正向匹配可在确认等价后使用引用键 `IN` 条件。否定、无关联、空引用，以及主表条件与外表条件混合的 `OR` 必须分别保留语义，不能统一改成正向 `IN`。例如“主记录紧急 OR 目标启用”转换后仍须保留主记录紧急分支；“没有关联目标”不能用任意目标字段筛选的补集代替。授权过滤始终限制整个结果集，不能被业务 `OR` 绕过。

不同连接分别读取，不用跨库 SQL JOIN、跨库子查询或视图绕过执行边界，也不把整个外库拉进 BFF。关系存在和 `sql validate` 通过都不能证明跨连接查询可执行。各库支持的过滤、投影、聚合可在所属库内完成；没有可验证的完整方案时停止，不能返回貌似完整的部分结果。

## 完整键、批量读取与拼接

以下步骤描述为已选定主记录补充展示字段的流程。参与筛选、排序或统计时先按上表确定读取顺序，再复用完整键与批量处理规则；不能把主表先分页当作所有跨库查询的前置步骤。

1. 从已授权主记录提取有效引用键。空值定义遵循字段合同，不用真值过滤误删合法的 `0`；复合键任一必需部分缺失时按缺失关系处理。
2. 保留 ID 精度及类型语义，不把大整数 ID 转成 `Number`。只有两端合同明确同一标识的不同编码方式时才做无损归一化；不擅自忽略大小写、前导零或空白。
3. 对完整键去重并按字段值比较。复合键保留字段顺序和类型，使用嵌套 `Map` 或明确的无损键编码，避免分隔符拼接碰撞；不能直接用新建数组作为 `Map` 查询键，因为数组按对象身份而非内容比较。例如期望 `(A, 7)`、`(B, 9)` 时，`region IN (A,B) AND external_id IN (7,9)` 会额外选中 `(A,9)`、`(B,7)`；应使用配对条件，或按第一个键分组后查询对应第二键集合，最终仍按完整键匹配。更多字段同样逐一配对，不省略剩余字段；示例字段不替代真实字段合同。
4. 键集合为空时跳过外表查询。非空时按目标接口的参数、分页和数量限制分批查询，投影只包含拼接和已授权输出所需字段。分批大小、最大页数、总读取量、并发和超时依据接口合同及业务预算确定，不复制其他项目的固定数值。
5. 每批都按该接口的分页合同读取完整结果，再建立映射。已知仍有后续结果却只拿到一页、完成前达到预算上限、页码不推进或查询失败时，默认返回错误，不推断剩余键均不存在。分批循环用于有界读取，不退回逐条记录的 N+1 调用。
6. 按已确认基数组装。1:1 或 N:1 的同一完整目标键出现多条记录时，报告重复匹配，不能用 `Map.set`、`Object.fromEntries` 或“取第一条”静默覆盖。一对多或多对多按合同保留集合，输出顺序须明确。

区分以下结果，不用 `catch(() => [])` 将错误伪装为空数据：

默认接口成功表示所需数据已完整读取。只有已有接口合同明确支持部分结果时，才使用其既定状态与字段输出；不能临时新增 `partial` 字段就返回成功，也不能把未完成计算的 `total`、排序或统计描述为准确结果。

| 情况 | 处理 |
|---|---|
| 完整查询成功，允许缺失的展示关系未匹配 | 保留主记录；单目标返回 `null`，多目标集合按业务合同返回 |
| 必需关系缺失或唯一关系重复匹配 | 按业务合同返回错误；不猜测替代记录 |
| 权限不足或查询失败 | 返回错误，不能解释为“目标不存在” |
| 分页结果不完整 | 默认返回错误；已有部分结果合同按上文处理，不能推断未读结果 |

## 授权与数据所有权

- BFF 从可信身份或已核验的服务端访问上下文确定权限。客户端提供的业务筛选值不能扩大授权范围；子记录需要沿已确认的父关系核验归属。
- 每个数据源分别落实访问控制。不能把主库的租户字段、门店字段、软删除字段或状态枚举机械套到目标表；关联键本身不是访问凭证，已取得的目标 ID 也不等于有权读取它。
- 核对 BFF 内部模型、SQL 或外部 API 的实际调用通道，不假设它必然经过 Dataset HTTP Hook。缺少授权合同则停止；复用公共授权函数前确认其输入、可信上下文和覆盖范围。
- 查询投影和返回值使用已授权字段白名单，敏感字段不得通过拼接结果、错误、日志或参数回显泄漏。保留业务字段的精度和空值语义，不为展示默认补零或改变标识符类型。
- 读写通道由数据所有权和接口合同决定。某个项目的外库只读、指定 OpenAPI 写入规则不能推广为所有外库的统一策略；确认关系或具备读取能力均不构成写入授权。

## 一致性与写入边界

分库读取不共享已证明的一致性快照。数据可能在两次读取之间变化；拼接结果不能作为库存、结算等关键写入的最终依据，关键校验应由权威写入服务在其一致性边界内完成。

`context.client.db.transaction` 的原子性仅按已核验的运行时事务范围理解，不能通过把调用放进同一个回调就承诺跨连接或外部 API 原子性。涉及多系统写入时先明确操作顺序、幂等、部分成功与补偿合同；状态未知时先核对，不盲目重试或自动补偿。事务 API 用法见 [Backend Function 事务规则](backend-function.md#事务规则)。

## 交付检查

- 两端连接、完整键、基数、权限、投影和读取预算都有明确依据；历史关系和同名字段没有被自动当成有效关系。
- 覆盖空键、复合键交叉组合与按值查找、重复匹配、允许/必需关系缺失、多页结果、读取中断及预算不足。
- 展示补充保留主表分页含义；关联筛选包含正向、否定、无关联和混合 OR 的反例，全局排序和统计不会用当前页结果替代完整结果。
- 用不同身份验证各端数据范围和字段输出；需要真实业务行数据或 BFF 执行验证时，按 [BFF 工作流](bff-creation-workflow.md)显式交接运行态验证。关系配置回读和 `bff push` 成功不能替代该验证。
