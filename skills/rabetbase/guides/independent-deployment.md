# 独立部署：开发、验证与排障

## 何时读取

仅在已确认独立部署并需要运行验证或厘清业务环境与平台连接的对应关系、出现平台到业务环境的同步疑点，或明确需要独立部署同步功能时读取。非独立部署应用只在 Lovrabet 平台内开发与验证，沿用普通工作流，不引入独立业务库或日常到线上的流程。

正常开发、绑定项目和正常 push 不查询或展示 `vipDeploy`。出现异常时，先确认平台是否保存、实际验证目标及失败步骤；已有证据定位其他原因时，不追加能力查询。

## 按需确认同步能力

需要判断显式同步能力时，用 [`app detail`](../references/rabetbase-app-detail.md) 读取 `app/getOne` 的 `vipDeploy`；选择器、输出与错误契约见命令参考。不从本地同名字段、CLI Domain、`rabetbase.domain-routing.json` 的 `mode` 或前端是否嵌入平台推断标识，也不用 `workspace init/use` 查询它。

- `true` 允许考虑显式同步功能，但不是故障证据、完成证明或执行授权；实际操作仍须满足对应权限与前提。
- `false` 不推荐显式同步恢复；`null` 或查询失败表示能力未确认。继续目标核对、平台回读及失败请求定位，不把未知当成关闭，也不回退本地值。
- 同一轮、同应用和平台连接复用查询结果；切换目标或结果可能变化时，仅在仍需要该事实的情况下重查。

`vipDeploy` 不提供业务环境地址、发布顺序或登录状态。保存后的自动同步由 `enableAutoSync` 及直连状态另行决定，不能由该标识的 true/false 推断自动同步是否开启；具体部署链路须另行确认。

## 确认连接与项目链路

无论应用是否独立部署，`rabetbase` 始终使用 `.rabetbase.json` 及现有配置解析机制访问 Lovrabet 平台服务端，沿用开发者认证；`vipDeploy` 仅用于 Agent 引导，不改变请求目标或认证方式，也不读取 `.lovrabet.json` 连接业务服务。`lovrabet` 使用 `.lovrabet.json` 对应的业务连接和业务账号 AccessKey。核对执行目录、所选应用和各 CLI 实际生效的配置，包括参数、环境变量等覆盖，并与页面实际请求目标对应。相同 AppCode 或 `env` 不证明连接同一环境，`env=production` 也不单独表示企业业务线上。

从项目已确认的部署约定获取同步目标和后续发布步骤。若项目明确“平台只连接业务日常，日常验证通过后按既有发布流程同步业务线上”，push 后先验证日常，线上单独核对发布。其他项目按各自约定处理，不猜环境数量、域名用途或发布顺序。已知事实一致时直接继续；信息缺失或冲突时先补齐，不切换另一环境试验，不复制两侧凭据或改写配置来消除错误。

### 理解用户说的“测试环境”与“线上环境”

企业应用的测试、日常与线上目标按项目部署约定确定；`.rabetbase.json` 的平台 `env` 定义见[配置参考](../references/rabetbase-config.md#顶层字段)。用户说“推测试环境”“更新日常”或“上线”时，沿用已确认的平台连接并核对业务目标，不据此改动平台 `env`。

- 项目对应关系已明确时，沿用当前正确的平台连接，按用户的业务目标执行和验证；不再让用户选择平台 `production` 还是 `daily`。只有用户明确要求切换 Lovrabet 平台环境，或已核实当前连接配置有误时，才按对应目标调整。
- 关系缺失或冲突时，只确认缺失的业务访问地址、目标应用或项目部署约定；不通过切换平台环境试错，也不要求用户先理解两套登录体系。`vipDeploy` 不能回答这些对应关系，无需为此重复查询。
- 业务线上发布遵循该项目已确认的发布流程；不能通过将 `env` 改为 `production` 代替发布，也不能将某个项目的导库流程套用到所有独立部署应用。

例如，项目已确认使用 Lovrabet 平台 `production`，且平台只同步到业务日常库时，用户要求“推测试环境”，可说明：“本次更新业务日常环境，沿用当前 Lovrabet 平台连接。推送后验证平台到业务日常的同步与运行结果；业务线上仍按既有发布流程处理。”这说明执行目标，不代表同步或运行验证已成功。

## 按实际环节定位

| 已确认的事实 | 下一步 |
|---|---|
| push 失败或响应丢失，平台保存结果未知 | 按[写入结果与恢复动作](conflict-detection.md#写入结果与恢复动作)先回读；确认未保存后解决原因，遵循原有冲突保护恢复必要的精确 push。后续步骤失败不抹去平台已保存事实 |
| 平台内容已新，独立业务目标库内容仍旧 | 核对平台到目标库的同步记录及同一资源的保存版本或内容；再次 push 不能替代这段同步的故障定位 |
| 仅页面表现或运行态返回版本仍旧，目标库保存内容未知 | 先确认请求目标及同一资源的目标保存事实，不能直接判定同步失败；缺少读取权限时明确该事实尚未确认 |
| 平台及目标库内容均已新，执行结果仍旧 | 转查请求目标、加载或执行行为；执行结果旧不证明存储旧，缓存只是待证实原因之一，不据此重推或补偿同步。本指南不展开缓存处理 |
| 日常已新，线上仍旧，且项目有这段发布流程 | 核对既有日常到线上发布记录及线上目标内容；不能据此判定平台保存或平台到日常同步失败，也不用平台补偿同步替代线上发布 |

没有目标保存证据时，明确“目标库是否收到新内容尚未确认”，交由有权限的人核查；不只查平台就宣布运行端已生效，也不凭标识假定双库同步。

显式任务的查询范围与结果解释见 [`deployment sync-all`](../references/rabetbase-deployment-sync-all.md#查询任务)。仅在确认属于初始化、回填或同步故障恢复且获授权时考虑该命令，遵循其能力、权限和安静窗口要求，不自动发起补偿。

## 认证、运行验证与反馈

认证失败先定位该请求的环境、接口及实际凭据，并确认目标确实提供所需研发接口；不能从业务运行域名推导另一套研发管理连接。平台开发者凭据、各业务环境的 CLI AccessKey、浏览器会话分别核验；同一账号也不代表 CLI 与浏览器会话同时有效。业务 CLI 认证失败只处理对应连接与凭据；只有正确平台开发接口明确认证失败才处理 `rabetbase` 登录，只有页面实际请求明确会话失效才引导该页面重新登录。404、权限不足和旧版本均不能直接归因为登录过期，不反复生成登录链接。

使用目标浏览器请求，或已连接同一业务环境且具备相应权限的 `lovrabet` 验证。BFF 的契约、参数、副作用及授权要求沿用[运行态 smoke](bff-creation-workflow.md#9-运行态-smoke按需)；无法执行时如实报告未验证。

Agent 负责区分上下文，无需要求用户先理解认证架构。只报告项目实际存在的环节及证据，例如“平台已保存，业务日常验证通过；线上更新需核对既有发布流程”，或“业务 CLI 的验证请求未通过认证，尚不能据此判断页面登录状态”。
